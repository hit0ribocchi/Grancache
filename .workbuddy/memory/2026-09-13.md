### 一次"副本内刷新"的真实时间线（17:04:20→17:04:39，**共 19 秒**）

40+ 个请求，其中 `game.granbluefantasy.jp` **几乎全部 BYPASS**，原因三类：

- `(set-cookie)` — 战斗页面 HTML：`/quest/content/newassist/0` 68.3KB、

**时间分解**：网络往返约 6-10 秒（40 请求 × 120-200ms，游戏是**串行**发的），

即：**卡主要来自"必须实时请求的不可缓存内容" × 上游 RTT**，代理无法消除。

在 3.5 秒内被**重复拉了两遍**，是游戏自身的重试逻辑。

### 排除掉的怀疑（别再重复查）

- Chrome 启动参数**正确**：`--proxy-pac-url` + `--disk-cache-size=2147483648` + `--disable-quic` 都在
- 上游连接**没有泄漏**：代理只维持 1 条到 0dcloud 的连接（netstat 里 38 条大部分是

## 时延实测：定位到「入口限速」是卡顿根因

新增 `tools/bench.mjs`（端到端时延基准，输出 min/中位/p90/max/标准差/抖动，
`direct` 参数可测直连做对照）。

### 关键测量结果

**1. 到 0dcloud 本地端口：0-1ms，零抖动**（30 次）→ 本地环节没问题。

**2. 经 0dcloud 到 `game.granbluefantasy.jp` 分段（15 次全新连接）**

```
CONNECT :   0   1   2   3     ← 始终完美
TLS     : 104 ... 157 [273] [420]
首字节  : 107 ... 217 [375] [610] [763] [894]
总计    : 220 ... 406 492 590 768 887 1016
```

**单调劣化**：前 10 次快（TLS 104-130ms、首字节 107-165ms），后 5 次劣化到 1 秒级。

**3. 分 4 轮 × 每轮 6 次、轮间隔 3 秒 —— 每轮都复现同样模式**

```
第1轮  266 283 383 453 [1034] [1914]
第2轮  299 309 372 852 881 [1717]
第3轮  239 246 261 321 378 831
第4轮  313 338 422 608 854 [1518]
```

**结论：这是入口限速（rate limiting）的典型特征** —— 短时间高频建连时，
前几次快、越往后排队越久；停 3 秒后恢复。游戏刷新恰好是「几十个请求挤在一起」，
正好撞上这个机制。**代理无法消除，因为瓶颈在 0dcloud 出口侧。**

**4. 直连对照（绕过代理，8 次）**：中位 315-372ms 但 p90 冲到 1117-5031ms。
说明问题**与代理无关**，代理转发（128-216ms）本身比直连还快。

### 因此的优化方向（代理侧能做的不多）

- **换 0dcloud 节点/线路**是唯一能根治的（用户侧操作）
- 减少并发建连数：让上游 Agent 复用而非新建 —— 已做（`maxFreeSockets:16`、
  `keepWarmSeconds` 已调成 20）
- 屏蔽埋点域名 —— 已做
- 真正未做的：**上游连接数上限再压低**（如 `maxSockets: 32`）避免瞬时并发建连触发限速

2. **不是"并发太多压垮自己"**：慢请求（≥p90=638ms）出现时前后 1.5s 的请求数均值

3. **真正的两类卡**：

     `connect.mobage.jp` 134 vs 921；`prd-game-...akamaized.net` 138 vs 749。
   - **上游服务器本身慢**（代理改不了）：`/party/deck/182` 是 `conn=110 up=9065`
     ——**建连只花 110ms，等响应等了 9 秒**。这是游戏后端在算数据。
4. **同一素材主机被同时开 6 条连接**：日志里 `17:46:40.974~984` 十毫秒内
   6 条 `TLS prd-game-a1-granbluefantasy.akamaized.net | 本机第 N 条下游连接`。
   这是 Chrome 对同一主机的默认并发上限。紧接着那批请求 `up` 从 110ms 涨到 750-900ms。
5. **`maxFreeSockets` 是 per-host 语义**（freeSockets 按 host 分桶），

### 决定性证据：单次刷新的墙钟 vs 请求耗时之和

用「请求间隔 >3s」切分"一次刷新"：

| 刷新时刻 | 请求数 | 墙钟耗时 | 各请求耗时之和 | 最慢单条 |
|---|---|---|---|---|
| 17:46:35 | **109** | **36.3s** | **38.2s** | 3134ms |
| 17:52:33 | 58 | 15.9s | 17.2s | 4548ms |
| 17:55:21 | 21 | 13.3s | 4.2s | 380ms |

**墙钟 ≈ 耗时之和 → 游戏是串行发请求的**（一个接一个不重叠）。
109 个 × 平均 350ms ≈ 38 秒。**这才是"卡"的全部来源——几十次往返的累加**，
不是某次特别慢。

### 裸链路实测（绕过代理，直连 0dcloud → 日服，12 次连续）

```
CONNECT : 0-2 ms
TLS     : 110-128 ms
首字节  : 107-166 ms
总计    : p50 229ms / p90 278ms / max 565ms    ← 12 次只 1 次抖动
```

**链路很稳**，单次 200–300ms 是到日服的固有 RTT。

### 关于那条 9065ms 的 `/party/deck/182`

- 同批（`_=` 时间戳差 1ms）、同主机：`/deckcombination/...` 只要 609ms → 差 15 倍
- 那 9 秒内**代理侧没有任何其它活动**（无重试/无并发/无错误）
- 裸测链路 p90 才 278ms
- → 只能是**游戏服务端对该聚合接口响应慢**（要汇总整队数据）

**表述修正**：之前说"游戏在算数据"方向对但不够准；
准确说法是"**游戏服务端对特定聚合接口的响应慢**"，
不是网络问题、不是代理问题。但更重要的是——

### 真正的结论（之前漏了）

**卡的来源是 40–109 次串行往返的累加。** 而这些请求
（`/rest/`、`/party/`、带 Set-Cookie 的页面）**全部不可缓存**。
代理缓存的素材（图片/音频）本来就不阻塞界面 ——
**真正阻塞界面的动态接口，恰恰是不能缓存的，所以"再加缓存"救不了这个卡。**

代理已到极限：命中 1ms、复用 81%、链路 p50 229ms 很稳。
想再快只能降低单次 RTT（换节点），代理侧没有空间了。

### 方法论沉淀

这次复核确立了一个关键判据：**不要只看单条最慢的请求，要统计
「单次刷新的墙钟 vs 请求耗时之和」**。两者接近 = 串行累加（客户端的锅+不可缓存的锅），
墙钟远小于和 = 并发良好。这比看 p90/max 更能说明"卡"的本质。
已写进 README 的「实测归因结论」。
